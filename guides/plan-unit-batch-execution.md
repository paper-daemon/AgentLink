# 作業は「計画単位」でまとめ、各段にレシートを残す

大きな作業を1つの巨大なリクエストとして実行すると、失敗したときに「どこまで出来て、どこで壊れたか」が分からず、最初からやり直しになります。権限の種類が違う操作を1つに束ねると、承認の粒度も崩れます。

このガイドは、作業を計画単位のバッチに分け、各段で検証と記録を残しながら進める型をまとめます。

## 型

### 1. 作業を「成功条件つきの段」に分ける

まず作業を小さな段に分解し、段ごとに成功条件を1つ書きます。接続できた／認証できた／操作できた／保存された／表示に反映された／再起動しても残っている、は全て別の成功条件です。1つの段に複数の成功条件が混ざっていたら、まだ分けが足りません。

### 2. バッチは「同じ承認の範囲」で束ねる

実行は、承認の範囲が同じ段だけを1バッチにまとめます。読み取りだけの段と、外部へ影響する段を同じバッチに入れません。束ね方を間違えると、「軽い確認のつもりで重い変更まで承認した」事故になります。

### 3. 各段は、次の段の前にレシートを残す

段が成功したら、その証拠（何をして、何が返って、どう確認したか）を残してから次へ進みます。バッチが途中で止まっても、レシートのある段までは完了として扱え、再開は続きからできます。

### 4. 失敗は段で止め、種類に名前を付ける

段が失敗したらバッチは止まりますが、計画全体は捨てません。失敗の種類（接続／認証／権限／相手側の拒否／自分の入力ミス）に名前を付けて記録します。次に試すときは、同じ失敗を繰り返すのではなく、名前の付いた前回とは違う手で試すためです。

### 5. 完了の宣言は、最後の検証の後

「実行した」と「確認できた」は別です。保存先を読み戻す、表示側で見える、再起動後に残っている、まで確認して初めて完了と言います。特に「成功の応答が返った」だけで完了にすると、実際には反映されていない差分が静かに残ります。

## 失敗のしかた

- **巨大な一括リクエスト**：権限も原因も違う問題が1つに混ざり、部分成功の切り分けができません
- **レシートなしの連続実行**：途中で止まると、済んだ段と済んでいない段の区別がつきません
- **失敗の連射**：同じ内容を繰り返し送って「突破したことにする」。相手側の制限や記録を壊すだけです
