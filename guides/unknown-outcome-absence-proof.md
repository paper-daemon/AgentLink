# 「結果不明」を終わらせる: 不存在の証明という考え方

外部APIへ「送ったはず」のリクエストがタイムアウトしたとき、一番危ないのは結果が分からないこと自体ではありません。分からないまま再送して二重に実行することと、逆に「分からない」を理由に永遠に止まってしまうこと、その両方です。

このガイドは、結果不明の副作用を「推測」で終わらせず、**不存在の証明**で決着させるための型をまとめます。一般論は [AI Agent Unknown-Outcome Recovery](./ai-agent-unknown-outcome-recovery.md) を先に読んでください。ここでは、その先の「どうやって不存在と言い切るか」だけを扱います。

## 型

### 1. 送る前に、意図を記録する

送信より前に「何を・どの識別子で送るか」を自分の側に記録します。識別子は相手側でも引ける安定したもの（クライアント側で付ける注文IDやリクエストID）を使います。送信後に記録したのでは、送信直前の障害で記録ごと消えます。

### 2. 結果不明になったら、まず識別子で引く

再送はしません。記録した識別子で相手側を照会します。ここで3つの答えがありえます。

- **存在し、状態が分かる** → その状態に合わせて続行・確定する
- **「存在しない」という確定応答** → 不存在が証明できた（次項）
- **それ以外のエラー**（タイムアウト、5xx、認証・制限エラー） → まだ結果不明。結論を出さない

### 3. 不存在と言えるのは、確定応答だけ

多くのAPIは、未知の識別子への照会に対して「存在しない」ことを示す専用のエラーを返します。この応答だけが「そのリクエストは届かなかった」という証明になります。逆に、通信エラーやサーバエラーは「分からない」という意味しか持ちません。エラーの種類を混同すると、届いていた処理を再送してしまいます。

### 4. 独立した面で裏取りする

確定応答に加えて、性質の違う面でも確認します。

- 未完了の一覧に、その識別子が無いこと
- 直近の履歴に、その実行が無いこと
- 残高や在庫など、副作用が起きていれば変わっていたはずの状態が変わっていないこと

複数が一致して初めて「無かったこと」を前提に動きます。

### 5. 再試行は「新しい意図」として

不存在が証明できたら、同じ処理の再実行は、新しい意図として記録し直してから送ります。古い意図には「不存在が証明済み」と残し、監査で追えるようにします。

### 6. 証明できないものは、見える場所に残す

不存在を証明できない結果不明は、解決したことにしません。未解決として一覧に残し、人の判断か、追加の証拠が揃うまで再送も破棄もしない。「自動でなかったことにする」が最悪の選択です。

## この型が使えない場所

- 識別子で照会する手段が無いAPI
- 「存在しない」の確定応答と他のエラーが区別できないAPI

この場合は、再送を自動化せず、照合を人の確認に回す設計が安全です。
